# Testing ConstructionFlow in Expo Snack

`ConstructionFlowSnack.js` is a single, self-contained file for testing the real ConstructionFlow
game in [Expo Snack](https://snack.expo.dev) with Expo Go — no local dev server needed.

## How to test

1. Open `snack/ConstructionFlowSnack.js` in this repo on GitHub.
2. Select All → Copy.
3. In Snack, select all of `App.js` → Paste over it.
4. In Snack's **Dependencies** panel, add `@react-native-async-storage/async-storage`
   (`@expo/vector-icons` is usually available by default).
5. Set Snack's **SDK version** (bottom-left) to **57**, matching the Expo Go app version this
   game targets.
6. Scan the QR code with Expo Go.

No other files or asset uploads are needed — all 50 equipment/office images load from this
repo's raw GitHub content instead of local requires.

## What's in this file

Generated by `scripts/build-snack-single.js` from the real, production game code:
`src/games/constructionflow/ConstructionFlowScreen.js`, plus any modules it imports from
`src/systems/`. Nothing is simplified or removed — the full game is in this one file with zero
local imports, and any imported system is inlined as its own isolated module (an IIFE, so its
internal helpers can't collide with the game screen's own top-level code).

As of Sprint 1 the screen imports **no** systems, so none are inlined: the 12 it used to pull in
were all inert (their output was written every day and read by nothing), and removing them cut
this file from 12,762 to 10,341 lines — a shorter copy-paste with no gameplay lost. The build
script derives what to inline from the screen's real imports, so if a system is ever genuinely
wired in it will be picked up automatically.

The production app in `src/app/` is unaffected — it keeps importing these files normally and
bundling assets locally (better for a shipped, offline-capable App Store build).

## Regenerating this file

After changing `ConstructionFlowScreen.js` or any of the systems it imports, run:

```bash
node scripts/build-snack-single.js
```

then commit the updated `snack/ConstructionFlowSnack.js`. No list to maintain — the script reads
ConstructionFlowScreen.js's own imports to decide what to inline.

Every regeneration self-verifies the properties Snack depends on (the default export survives,
no local imports or asset `require()`s remain, every asset resolves to a raw GitHub URI) and
exits non-zero if any of them break, so a malformed build can't reach the device.
